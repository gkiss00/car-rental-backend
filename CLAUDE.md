# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

This is the backend for a car rental application. Only the backend is developed in this repository.

Stack:
- Java 25
- Spring Boot 4 (via `spring-boot-starter-parent`)
- MongoDB (Spring Data MongoDB)
- Lombok (`@Getter`/`@Setter`/`@Builder`/...)
- Spring Security with stateless JWT authentication
- Contract-first API: every exposed endpoint is defined in `src/main/resources/openapi/api.yaml`, and Java API interfaces + models are generated from it at build time (`openapi-generator-maven-plugin`, generator `spring`, `interfaceOnly=true`). Controllers implement the generated interfaces rather than declaring their own `@RequestMapping`s. Generated code lands in `target/generated-sources/openapi` (gitignored) under packages `org.kiss.api` (interfaces) and `org.kiss.api.model` (DTOs/enums).

## Architecture

- `org.kiss.CarRentalApplication` — Spring Boot entry point (`@SpringBootApplication`, `@ConfigurationPropertiesScan`).
- Packages are organized by layer, not by feature: `org.kiss.model.entity` (Mongo `@Document` entities only — `User`, `Company`, `Car`, `CarType`), `org.kiss.model.entity.util` (each entity's enums and embedded/value objects, e.g. `Role`, `CarStatus`, `CarCategory`, `TransmissionType`, `FuelType`, `CarLocation`, `CompanyStatus`, `CompanyAddress`), `org.kiss.repository` (Spring Data `MongoRepository` interfaces, plus custom-repository pairs and query-criteria records, e.g. `CarRepository`/`CarRepositoryCustom`/`CarRepositoryImpl`/`CarSearchCriteria`), `org.kiss.mapper` (all entity↔generated-DTO mapping, e.g. `UserMapper`, `CarMapper` — services must not build entities or response DTOs inline, that logic belongs in a mapper), `org.kiss.service`, `org.kiss.controller`, `org.kiss.security`, `org.kiss.exception`. Follow this layout for new domain objects: the `@Document` class itself goes directly in `org.kiss.model.entity`, anything it merely uses (enum, embedded value type) goes in `.util`.
- `org.kiss.security` — JWT infrastructure: `JwtProperties` (`app.jwt.*` config), `JwtService` (issues/parses HS256 tokens via `jjwt`), `JwtAuthenticationFilter` (reads the `Authorization: Bearer` header, populates `SecurityContext` with an authority of `ROLE_<role>` from the token's `role` claim — no DB lookup per request), `SecurityConfig` (stateless `SecurityFilterChain`, `@EnableMethodSecurity` so future endpoints can use `@PreAuthorize("hasRole('ADMIN')")` etc.).
- `org.kiss.service.AuthService` — signup/signin business logic (password hashing via `BCryptPasswordEncoder`, JWT issuance). Auth failures use Spring Security's `BadCredentialsException`; a custom `EmailAlreadyInUseException` covers duplicate signups.
- `org.kiss.controller` — REST controllers implementing the generated API interfaces (`AuthController implements AuthApi`, `UsersController implements UsersApi`, `PingController implements PingApi`).
- `org.kiss.exception.GlobalExceptionHandler` — `@RestControllerAdvice` mapping domain/validation/auth exceptions to the generated `ErrorResponse` schema.
- `org.kiss.storage` — Cloudflare R2 (S3-compatible) infrastructure, parallel to `org.kiss.security`: `StorageProperties` (`storage.*` config: `bucketName`, `region` — always `"auto"` for R2, `endpoint`, `accessKey`, `secretKey`, `publicUrl`), `StorageConfig` (builds the `S3Presigner` bean — region/endpoint/credentials from `StorageProperties`, `S3Configuration.pathStyleAccessEnabled(true)` since R2 doesn't support virtual-hosted-style bucket URLs), `StorageService` (`generateUploadUrl(objectKey)` — a presigned PUT URL, 10-minute TTL, single use; `publicUrlFor(objectKey)` — deterministic public read URL, `storage.publicUrl` + key). Assumes the R2 bucket has public read access configured (custom domain or `.r2.dev`) — `publicUrl` needs to actually point at that, the checked-in `application.yml` default (`https://pub-CHANGE-ME.r2.dev`) is a placeholder.

### Auth model

Three roles: `USER` (normal renter), `DEALERSHIP` (car dealership account), `ADMIN`. Public signup (`POST /api/auth/signup`) only accepts `RegistrableRole` (`USER` or `DEALERSHIP`) — admin accounts are not self-service, and signup never attaches a `companyId`. `POST /api/users` (`CreateUserRequest`, full `UserRole`) additionally lets an authenticated `ADMIN` or `DEALERSHIP` account create a user directly (no JWT returned — this creates an account for someone else, it isn't a login): admins may set any role, but `UserService.createUser` rejects a `DEALERSHIP` caller's attempt to create an `ADMIN` account with `AccessDeniedException` (checked via the caller's `ROLE_ADMIN` authority, not a DB lookup). `GET /api/users` (admin-only, paginated) takes an optional `search` param matching case-insensitively against first name, last name, or email (a single Spring Data derived query with the same term repeated across an `Or`/`Containing`/`IgnoreCase` method on `UserRepository` — no custom Mongo query needed). `UserService` also backs `GET /api/users/me` and `PUT /api/users/me/password` (any authenticated user changing their own password; requires the current password, mismatches throw `InvalidCurrentPasswordException` → 400 — note there's no token revocation, so a password change does not invalidate already-issued JWTs before they expire). `POST /api/auth/signin` returns a bearer JWT; the token's `role` claim drives authorization for subsequent requests. `/api/auth/**`, `/api/ping`, and `GET /api/cars`/`GET /api/cars/{id}` are public; everything else requires a valid bearer token (see `SecurityConfig`). Note the OpenAPI spec has always documented both those `GET` car endpoints as "Public" (no `security:` block), but `SecurityConfig` never actually granted that until now — a controller method having no `@PreAuthorize` only skips the *role* check, Spring Security's default `anyRequest().authenticated()` still blocks anonymous callers unless the path is explicitly `permitAll()`'d.

### Company model

`Company` (`org.kiss.model.entity.Company`) represents a car rental business and is distinct from `User`. The entity holds a single `userIds` list — every user attached to the company, regardless of role; there is no separate "owner" concept at the company level any more (dropped in favor of a single list; a user's own `role` on `User` is what determines what they're allowed to do). Any id given in `userIds` at create or update time must reference an existing `User` (`InvalidCompanyUserException`, 400, otherwise — existence only, no role restriction). `CompanyResponse` (the full-detail view, i.e. everything except `CompanySummaryResponse` from `GET /api/companies`) exposes `users` — the resolved `UserProfileResponse` for each id, not the raw ids — so `CompanyService` always fetches `userRepository.findAllById(company.getUserIds())` before calling `CompanyMapper.toResponse(company, users)`; `CompanyMapper` stays a pure transformer (it only knows how to map an already-fetched `List<User>`, it never queries the repository itself). Only `ADMIN` accounts can create companies (`POST /api/companies`, `@PreAuthorize("hasRole('ADMIN')")`). `CompanyRegistrationRequest` only requires `name` — `userIds`, `email`, `address`, etc. are all optional, so `CompanyMapper`/`CompanyService` must stay null-safe for all of them (a company can be created with no users and get staffed later via `POST /api/users`, and `CompanySummaryResponse.city`/`country` are only populated when an address was actually given). New companies start `PENDING_VERIFICATION`; `PATCH /api/companies/{id}` (admin-only, `CompanyUpdateRequest` — every field optional, only fields present in the request are applied, validated the same way as `POST /api/companies`) is currently the only way to move a company to `ACTIVE`/`SUSPENDED` via `status`; nothing else enforces the status against other actions (e.g. a `PENDING_VERIFICATION` company can still have cars registered against its users). Updating `userIds` via `PATCH /api/companies/{id}` replaces the list wholesale but does **not** touch the affected users' `User.companyId` — that PATCH only ever mutates the `Company` side. `PUT /api/companies/{id}/users/{userId}` (admin-only, `CompanyService.addUserToCompany`) and `DELETE /api/companies/{id}/users/{userId}` (admin-only, `CompanyService.removeUserFromCompany`) are the operations that keep both sides consistent — plain `PATCH` never touches `User.companyId`. `addUserToCompany` adds the user to the target company's `userIds`, sets `User.companyId` to match, and — if the user previously belonged to a different company — removes them from that old company's `userIds` first; it rejects `ADMIN`-role users (`InvalidCompanyUserException`, 400, since admins aren't company-scoped) and is idempotent (adding an already-attached user is a no-op). `removeUserFromCompany` removes the id from the company's `userIds` and clears `User.companyId` only if it currently points at that same company (so it won't clobber a link that was already repointed elsewhere); it's idempotent too — removing a user who isn't currently a member is a no-op, not an error. Both return the updated `CompanyResponse` (200), and 404 if either the company or the user id doesn't exist. `Car.companyId` links every car to a `Company` (see the `CarType`/car section below) — there is no more per-user car ownership.

`User.companyId` links a user to its company (null for `ADMIN`s and for anyone created via public signup, since that flow never sets it). `UserService.createUser` populates both sides when creating a `USER`/`DEALERSHIP` account:
- Caller is `ADMIN`: `companyId` must be present in the request and reference an existing company (`CompanyIdRequiredException`/`CompanyNotFoundException` otherwise, both 400/404).
- Caller is `DEALERSHIP`: any `companyId` in the request is ignored — the new user is always attached to the caller's own company (looked up via the caller's own `User.companyId`). If the caller has no company of their own, `DealershipWithoutCompanyException` (400).
- Either way, the new user's id is added to the company's `userIds` (`UserService.addUserToCompany`).

### CarType

`CarType` (`org.kiss.model.entity.CarType`, collection `car_types`) is a standalone reference entity — `id`, `make`, `model` — with a unique compound index on `(make, model)` (`@CompoundIndex`, since Mongo's per-field `@Indexed(unique = true)` can't express a uniqueness constraint spanning two fields). Admin-only CRUD-lite: `GET /api/car-types` (paginated, sorted by make then model), `POST /api/car-types` (`CarTypeAlreadyExistsException` → 409 on a duplicate make/model pair), `DELETE /api/car-types/{id}` (`CarTypeNotFoundException` → 404). No `GET /api/car-types/{id}` — not requested, so not added. `Car.make`/`Car.model` are still free-text strings, not a foreign key to `CarType` — but `CarService.registerCar` validates the pair against `CarTypeRepository.existsByMakeAndModel` (case-sensitive exact match) and throws `UnknownCarTypeException` (400) if that combination was never registered as a `CarType`. This check only runs at car **creation** (`POST /api/cars`), not at `updateCar` — a car's make/model can currently be edited to an arbitrary value via `PUT /api/cars/{id}` without re-validating against `CarType`.

`CarType.previewUrl` and `POST /api/car-types`'s direct-upload flow (the first use of `org.kiss.storage`): `createCarType` pre-generates the `CarType`'s id itself (`new ObjectId().toHexString()`, not left to Mongo) so it can derive a deterministic object key (`car-types/{id}/preview`) *before* the first save. It sets `previewUrl` (`StorageService.publicUrlFor`) on the entity immediately — meaning `previewUrl` exists and is returned before the image is actually uploaded, and will 404 until the frontend PUTs to the presigned URL — and returns both the created `CarTypeResponse` and a one-time `previewUploadUrl` (`StorageService.generateUploadUrl`, 10-minute presigned PUT) wrapped in `CarTypeCreationResponse`, a schema used only by this endpoint (not `CarTypePage`/get-by-id, since a presigned upload URL must never be cached or replayed on a later read — there's no `GET /api/car-types/{id}` yet anyway). There's no re-upload/replace endpoint yet if the initial upload fails or needs replacing.

`Car` has no per-user owner any more — `Car.companyId` (the former `Car.dealershipId` was removed entirely) is the sole ownership link, always pointing at a `Company`. `POST /api/cars` accepts both `ADMIN` and `DEALERSHIP` callers (`CarController.registerCar`, `@PreAuthorize("hasAnyRole('ADMIN', 'DEALERSHIP')")`), and `CarService.registerCar` branches on the caller's role: a `DEALERSHIP` caller gets `companyId` derived from their own company (`CurrentUserService.getCallerCompany()` — `DealershipWithoutCompanyException` 400 if they don't have one), while an `ADMIN` caller must supply `CarRegistrationRequest.companyId` explicitly (`CompanyIdRequiredException`/`CompanyNotFoundException` otherwise, 400/404). Because ownership is now company-scoped rather than per-user, `updateCar`, `deleteCar`, and `listCarsForCurrentDealership` (`GET /api/cars/mine`) all compare/filter against the caller's own company id — so **any** `DEALERSHIP` user belonging to the same company can update, delete, or see a car another user of that company registered (or an admin registered on the company's behalf), not just the original creator. `PUT /api/cars/{id}` and `DELETE /api/cars/{id}` (`@PreAuthorize("hasAnyRole('ADMIN', 'DEALERSHIP')")`) let `ADMIN` update/delete any car unconditionally — both `CarService.updateCar` and `CarService.deleteCar` only run the company-ownership check (`requireOwnedByCallerCompany`) when `!currentUserService.isAdmin()`.

`CurrentUserService` (`org.kiss.service`) centralizes "who is the caller" logic shared by `UserService` and `CarService`: `getCallerUser()` (looks up the `User` behind the JWT's email), `getCallerCompany()` (that user's `Company`, `DealershipWithoutCompanyException` if `User.companyId` is unset), `isAdmin()` (checks the `ROLE_ADMIN` authority already present in the JWT-derived `SecurityContext`, no DB call). Any future service needing "the caller's own company" or "is the caller an admin" should use this rather than re-deriving it.

### Reservation

`Reservation` (`org.kiss.model.entity.Reservation`, collection `reservations`) — `id`, `carId`, `startTime`, `endTime` (both `Instant`). `POST /api/reservations` (`ReservationController`/`ReservationService`, any authenticated role — `ADMIN`, `DEALERSHIP`, or `USER`) creates one:
- **Access**: `ADMIN` may reserve any car. Otherwise (`DEALERSHIP` or `USER`) the caller must have a company (`CurrentUserService.getCallerCompany()`, `DealershipWithoutCompanyException` 400 if not — this applies to `USER` accounts too, so a plain customer with no `companyId` currently cannot create a reservation at all) and that company must match the target car's `companyId` (`AccessDeniedException` 403 otherwise). There is deliberately no separate role check here beyond that.
- **Validation**: `endTime` must be after `startTime` (`InvalidReservationPeriodException`, 400). Every other reservation for the *same car* must be separated from the new one by at least a 2-hour gap on one side or the other (`ReservationConflictException`, 409) — checked by fetching all of that car's reservations via `ReservationRepository.findByCarId` and comparing in memory (`ReservationService.requireNoConflict`), not via a Mongo query; this single gap check subsumes plain overlap detection (an overlap always fails the 2-hour-gap test too), so there's no separate overlap check.
- The same access rule (a private `ReservationService.requireCarAccessible`, mirroring `CarService`'s `requireOwnedByCallerCompany`) gates every other reservation endpoint too: `GET /api/cars/{carId}/reservations` (paginated, sorted by `startTime`), `GET /api/reservations/{id}`, `PUT /api/reservations/{id}`, `DELETE /api/reservations/{id}` — all check access via the reservation's *current* `carId`. `updateReservation` reuses `CreateReservationRequest` as its body (full replace, including `carId`) rather than a separate update schema, since every field is meaningful for a reservation and there's no natural "partial" reservation update; if the update changes `carId` to a different car, access is checked against **both** the old and the new car (so you can't use an update to move a reservation onto a car outside your company), and the conflict check runs against the new car's other reservations, excluding the reservation being updated itself (`requireNoConflict`'s `excludeReservationId` parameter).
- `GET /api/companies/{companyId}/reservations` (paginated, sorted by `startTime`) lists reservations across *all* of a company's cars — `ReservationService.listReservationsForCompany` resolves the company's car ids via `CarRepository.findByCompanyId(companyId)` (an unpaginated `List<Car>` overload alongside the existing paginated one) then queries `ReservationRepository.findByCarIdIn`. Its own access check, `requireCompanyAccessible` (404 via `CompanyNotFoundException` if the company doesn't exist, then the same admin-bypass-or-must-be-your-own-company rule as `requireCarAccessible`), is a separate private method from `requireCarAccessible` — they check different things (a company id vs. a car's `companyId`) even though the underlying rule is identical.
- Not tracked: who created a reservation (no `userId`/`companyId` stored on `Reservation` itself, only `carId`).
- `GET /api/cars` (`listCars`) has two optional query params, `availableFrom`/`availableUntil` (must be given together, `availableUntil` after `availableFrom`, else `InvalidReservationPeriodException` 400 — reused from the reservation feature via its second, message-taking constructor). When set, `CarService.resolveCarsUnavailableForPeriod` finds every reservation that could conflict with that window under the same 2-hour buffer rule as reservation creation (`ReservationRepository.findByStartTimeLessThanAndEndTimeGreaterThan`, a single derived-query range condition — algebraically the negation of the two-branch check in `ReservationService.requireNoConflict`, so if that buffer or conflict rule ever changes, this needs to change with it), collects the distinct `carId`s, and passes them to `CarRepositoryCustom.search` as a new `excludedCarIds` parameter (`Criteria.where("id").nin(...)`, skipped when empty). This keeps `CarRepositoryImpl` itself unaware of the `reservations` collection — the cross-collection lookup lives in `CarService`, not the repository.

### Insurance

`Insurance` (`org.kiss.model.entity.Insurance`, collection `insurances`) is a catalog entity for insurance tiers offered by the platform (e.g. "Basic"/"Standard"/"Premium") — `id`, `name` (unique, `@Indexed`), `coveragePoints` (`List<CoveragePoint>`, in `org.kiss.model.entity.util`: a `label` + a `covered` boolean per point, so tiers can be rendered as a feature-comparison table by using the same set of labels across tiers — not structurally enforced, just a data-entry convention), `dailyPriceAmount`, `dailyPriceCurrency`, `hasFranchise` (boolean) + `franchiseAmount` (the deductible/excess payable by the renter, only meaningful when `hasFranchise` is true — not enforced, e.g. nothing currently stops `franchiseAmount` being set while `hasFranchise` is false). Not a per-car policy record — unrelated to `Car`/`Reservation` for now. Full CRUD now exists: `GET /api/insurances` (paginated, sorted by `name`) and `GET /api/insurances/{id}` are **public** — no `@PreAuthorize`, and (like `GET /api/cars`/`GET /api/cars/{id}`) explicitly `permitAll()`'d in `SecurityConfig`, since a controller method with no `@PreAuthorize` only skips the role check, not Spring Security's default `anyRequest().authenticated()`. `POST`/`PUT`/`DELETE /api/insurances/{id}` are admin-only (`@PreAuthorize("hasRole('ADMIN')")`): `InsuranceAlreadyExistsException` (409) on a duplicate `name` at create or update (update's check is skipped when the name is unchanged, same pattern as `CompanyService.updateCompany`'s registration-number check), `InsuranceNotFoundException` (404) otherwise. `updateInsurance` reuses `InsuranceRequest` as a full-replace body (like `ReservationController.updateReservation` reuses `CreateReservationRequest`) rather than a separate update schema. Still nothing links an `Insurance` to a `Car`/`Reservation`.

### Adding a new endpoint

1. Add the path + schemas to `src/main/resources/openapi/api.yaml`.
2. Run the build so `openapi-generator-maven-plugin` regenerates the interface/models.
3. Write a controller implementing the generated `*Api` interface; use `@PreAuthorize` on controller methods for role restrictions beyond "authenticated".
4. For resource-level ownership checks that `@PreAuthorize` can't express cleanly (e.g. `CarService.updateCar` requiring the car's `companyId` to match the caller's own company), load the resource in the service and throw Spring Security's `AccessDeniedException` directly — `GlobalExceptionHandler` already maps it to a 403 `ErrorResponse`.

## Commands

- Compile (also regenerates OpenAPI sources): `mvn compile`
- Package: `mvn package`
- Run: `mvn spring-boot:run` (connects to the Atlas cluster at `spring.mongodb.uri` in `application.yml`, auth via `DB_USERNAME`/`DB_PASSWORD` env vars — note: Spring Boot 4 renamed this property from `spring.data.mongodb.uri`/`spring.data.mongodb.database` to `spring.mongodb.uri`/`spring.mongodb.database`; the old `spring.data.mongodb.*` keys are silently ignored, not bound, which silently falls back to the driver's default `mongodb://localhost/test`)
- No test sources exist yet (`src/test` is absent), though `spring-boot-starter-test` and `spring-security-test` are already on the test classpath.
- JWT signing secret/expiry are configurable via `JWT_SECRET` / `JWT_EXPIRATION_MS` env vars (see `application.yml`); the checked-in default secret is dev-only.

## Deployment

Deploys as a Docker web service (`Dockerfile` at the repo root — multi-stage: `eclipse-temurin:25-jdk` + Maven to build the jar, `eclipse-temurin:25-jre` to run it; `render.yaml` defines the service as a Render Blueprint, though the same `Dockerfile` also builds on Railway without extra config). The host injects its own `PORT` env var at runtime, which `application.yml`'s `server.port: ${PORT:8080}` reads (falling back to 8080 for local runs where `PORT` isn't set). Secrets (`DB_USERNAME`, `DB_PASSWORD`, `JWT_SECRET`, `STORAGE_ACCESS_KEY`, `STORAGE_SECRET_KEY`, `STORAGE_PUBLIC_URL`) are set directly in the hosting platform's dashboard, not committed (`sync: false` in `render.yaml`). The MongoDB Atlas cluster's Network Access list must allow the host's outbound traffic — neither Render's nor Railway's free/starter-tier outbound IPs are static, so this generally means allow-listing `0.0.0.0/0` on the Atlas cluster and relying on the DB credentials for access control. The `Dockerfile`'s `ENTRYPOINT` also forces `-Djdk.tls.client.protocols=TLSv1.2`: Java 11+'s default TLS 1.3 handshake gets rejected by MongoDB Atlas's shared-tier (M0/M2/M5) TLS-routing proxy with `SSLException: Received fatal alert: internal_error` from some hosting platforms' networking — this is MongoDB's own documented workaround, not specific to one host.

## Working notes

- The user prefers to run Maven builds themselves rather than have Claude invoke `mvn` — write/update code based on known `openapi-generator`/Spring conventions and let the user compile, reporting fixes if they hit errors, instead of proactively shelling out to `mvn`.
